## SMS Alert Simulation System Design

### System Diagram
![architecture](/images/system-overview.png)

### Component requirements
**Producer Service**
* Generate a configurable number of random SMS messages (default 1000)
* Each message contains up to 100 random characters
* Simulates production by an adjustable rate (number of messages/second)

**Message Broker Service**
* Receives messages from the producer
* Routes incoming messages to Python standard-library `collections.deque` queues keyed by their validated `message_type`, creating each queue on first use
* Enforces one capacity limit across all pending messages and preserves FIFO order within each type's queue
* Assigns work from the queue selected by the sender's requested message type
* Runs as a single broker process that owns the shared in-memory queue; queued work is lost on restart
* Confines all broker state access to one event-loop thread; `async def` API handlers call synchronous broker methods directly, with no yielding during queue or duplicate-record updates

**Sender Service**
* Receives assigned messages from the message broker
* Sends the messages 
* Creates a configurable number of individual senders
* Each sender waits a random time before sending (with a configurable mean)
* Each sender has a configurable failure rate
* The sender simulates the wait time before the sender determines whether
to randomly fail the message. 

**Metrics Aggregator**
* Stores metrics from the sender service.
* Provides APIs to query metrics

### Example flow
1. Producer generates sms messages and calls the message broker API
2. The message broker queues the incoming messages
3. The message broker assigns one queued message with attempt metadata to an available sender
4. The sender service calls the metrics aggregator service with metrics about the sms message

### How the design supports maximum concurrency and throughput
By splitting out each service separately, each service can independently scale as needed.
For example, the number of producers can be increased to call the message broker. 
The message broker can support multiple or larger queues. The sender service can launch more
individual senders. 

### Libraries used
For this design, everything is written in Python and can be run locally. 

#### Message Broker Service
* Python standard-library `collections.deque` for in-memory FIFO queues, one per message type
* FastAPI

#### Metrics Aggregator
* FastAPI
* SQLite

### Message schemas

Every message contract requires `message_type` with the literal value
`sms_message`. The attempt envelope repeats the nested message's type; sender
results retain it alongside their distinct `event_type`. This is a revision of
the draft version-one schemas; existing clients must update their payloads.

#### SMS message

The producer creates one payload for each SMS:

```json
{
  "schema_version": 1,
  "message_type": "sms_message",
  "message_id": "d29201ba-4518-41cf-855c-c85038fcda77",
  "created_at": "2026-09-26T14:30:00.123Z",
  "body": "Example simulated SMS"
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `schema_version` | Integer | Payload format version; initially `1`. |
| `message_type` | Literal string | `sms_message`, identifying the kind of message for routing. |
| `message_id` | UUID string | Unique message identifier, generated by the producer and preserved through retries. |
| `created_at` | UTC timestamp string | Time the producer created the message, used to calculate total delivery latency. |
| `body` | String | SMS text containing up to 100 characters. |

The producer generates a unique message ID for each new message. The broker uses
that ID alone for duplicate detection throughout its lifetime. Messages and
metrics do not carry a simulation-run grouping identifier.

#### Message Broker attempt

When the broker assigns a message to a sender, it wraps the original SMS payload with attempt metadata:

```json
{
  "schema_version": 1,
  "message_type": "sms_message",
  "attempt_id": "a6da2cee-1487-48da-bf1d-9145e095cd85",
  "attempt_number": 1,
  "enqueued_at": "2026-09-26T14:30:00.130Z",
  "dispatched_at": "2026-09-26T14:30:00.150Z",
  "message": {
    "schema_version": 1,
    "message_type": "sms_message",
    "message_id": "d29201ba-4518-41cf-855c-c85038fcda77",
    "created_at": "2026-09-26T14:30:00.123Z",
    "body": "Example simulated SMS"
  }
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `schema_version` | Integer | Delivery envelope format version; initially `1`. |
| `message_type` | Literal string | `sms_message`, matching the nested message's type. |
| `attempt_id` | UUID string | Unique identifier for this delivery attempt. |
| `attempt_number` | Integer | Attempt count for the message, starting at `1`. |
| `enqueued_at` | UTC timestamp string | Time the work for this attempt entered the broker's queue. |
| `dispatched_at` | UTC timestamp string | Time the broker dispatched this attempt to a sender. |
| `message` | SMS message object | Original, unchanged SMS payload. |

The broker owns attempt metadata. If retries are enabled, each new attempt receives a new attempt ID, an incremented attempt number, and new queue and dispatch timestamps. The message ID and message type remain unchanged.

#### Sender result

After processing an attempt, the sender reports its outcome to the metrics aggregator:

```json
{
  "schema_version": 1,
  "message_type": "sms_message",
  "event_id": "75d7cd30-ec80-4357-b57b-fbd2c3ef08ea",
  "event_type": "sms.attempt_completed",
  "message_id": "d29201ba-4518-41cf-855c-c85038fcda77",
  "attempt_id": "a6da2cee-1487-48da-bf1d-9145e095cd85",
  "sender_id": "sender-3",
  "occurred_at": "2026-09-26T14:30:00.400Z",
  "status": "failed",
  "processing_duration_ms": 250,
  "total_latency_ms": 277,
  "error_code": "SIMULATED_SEND_FAILURE"
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `schema_version` | Integer | Result event format version; initially `1`. |
| `message_type` | Literal string | `sms_message`, identifying the original message's type. |
| `event_id` | UUID string | Unique metric event identifier, used to discard duplicate submissions. |
| `event_type` | String | `sms.attempt_completed` for a completed sending attempt. |
| `message_id` | UUID string | Identifies the original SMS. |
| `attempt_id` | UUID string | Identifies the delivery attempt that produced this result. |
| `sender_id` | String | Identifies the individual sender that processed the attempt. |
| `occurred_at` | UTC timestamp string | Time the sending attempt finished. |
| `status` | String | Either `sent` or `failed`, describing this attempt's outcome. |
| `processing_duration_ms` | Nonnegative number | Elapsed processing time in milliseconds, including the simulated sending delay. |
| `total_latency_ms` | Nonnegative number or null | End-to-end elapsed time from the message's `created_at` timestamp until the attempt completed. This field is optional for compatibility with earlier clients; `null` means no latency sample is available. |
| `error_code` | String or null | Failure reason, such as `SIMULATED_SEND_FAILURE`; `null` on success. |
